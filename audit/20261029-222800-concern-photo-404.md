# Audit: Fix concern photo 404

**Date**: 2026-10-29 22:28
**Task**: Concern images returned 404 instead of loading.

## Files Changed
| File | Changes |
|------|---------|
| `backend/app/Concerns/Resources/ConcernResource.php` | `photo_url` is now a relative `/storage/{path}` instead of `Storage::disk('public')->url()` (which used `APP_URL`); removed unused `Storage` import |
| `frontend/src/concerns/api.ts` | `mediaUrl()` rewrites absolute `/storage/...` URLs onto the API origin as a safeguard |

## Summary

**Root cause:** `backend/.env` has `APP_URL=http://localhost` (no port) while the API runs at `http://localhost:8000`. `Storage::disk('public')->url()` builds `http://localhost/storage/concerns/...`, so the browser requested port 80 and got a 404. The file itself was served correctly at `http://localhost:8000/storage/...`.

**Fix:** the API now returns a relative `photo_url` (`/storage/concerns/...`), and the frontend's `mediaUrl()` prefixes the API origin (`http://localhost:8000`). It also rewrites any absolute `/storage/` URL to the API origin, so a mismatched `APP_URL` can no longer break images.

- `http://127.0.0.1:8000/storage/concerns/h0mq...png` → 200; `http://localhost/storage/...` → 404 (the old URL)
- Browser (educ, `/office/concerns`): `<img>` loads with `naturalWidth=565`, `complete=true`, **0 responses with 404**, no console errors
- `php artisan test` → **87 passed** (403 assertions)

## Notes
