## Summary

Concerns are now a real module. Any logged-in user can report a problem with a location, description and optional photo. Admin reviews them in a status-priority queue (Open → Acknowledged → Resolved) and can Acknowledge, Resolve or Reopen. Offices see only concerns at their office location and report from a form that pre-fills and locks their location. Maintenance can report and only sees its own submissions.

**Endpoints**
- `GET /api/concerns` — search, status filter, pagination; admin = all, office = office location, maintenance = own reports
- `GET /api/concerns/locations` — selectable locations (office gets only its own)
- `POST /api/concerns` — multipart, optional photo; office `location_id` forced server-side
- `GET /api/concerns/{id}` — scoped detail
- `PATCH /api/concerns/{id}/status` — admin only; sets/clears `resolved_at`

## Notes
- Photos are stored on the `public` disk under `concerns/`; the resource returns a relative `/storage/...` URL and the frontend prefixes the API origin.
- No delete endpoint — resolved concerns stay as history, matching the no-hard-deletes direction.
- `resolved_at` is set on first resolve and cleared if a concern is reopened.
- Seed runs under `WithoutModelEvents`, so seeded concerns do not flood the audit log; real actions are logged.
